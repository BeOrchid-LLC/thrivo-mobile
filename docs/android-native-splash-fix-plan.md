# Fix native Android splash: eliminate dark screen + white box

## Context

Across this session we've iterated on `thrivo-mobile`'s native Android splash screen to make it a brief, invisible flash that hands off to the JS-controlled `BrandSplash` component. Two prior fixes landed already (native splash background matched to `#F4F6F9`, transparent placeholder icon so Android 12+'s SplashScreen API — which hard-requires an icon drawable to build at all — doesn't show a real logo, and `SplashScreen.hideAsync()` moved onto the root view's `onLayout` so it fires the instant the first JS frame paints instead of waiting on font load). Despite that, the user is still seeing a **dark background with a small floating white box for 3-5 seconds** before the app's welcome screen appears, on a device in system dark mode. We also independently confirmed (via Android's own `ActivityTaskManager: Displayed ... +5s098ms` logcat line) that cold-start genuinely takes ~5s on this device — a real but *separate* performance question the user explicitly asked to set aside until this visual bug is fixed first.

Direct inspection of the generated (gitignored, CNG-managed) `android/app/src/main/res/values/styles.xml` found the likely root cause:

```xml
<style name="AppTheme" parent="Theme.AppCompat.DayNight.NoActionBar">
  <item name="android:enforceNavigationBarContrast" tools:targetApi="29">true</item>
  <item name="android:editTextBackground">@drawable/rn_edit_text_material</item>
  <item name="colorPrimary">@color/colorPrimary</item>
  <item name="android:statusBarColor">#F4F6F9</item>
</style>
<style name="Theme.App.SplashScreen" parent="Theme.SplashScreen">
  <item name="windowSplashScreenBackground">@color/splashscreen_background</item>
  <item name="windowSplashScreenAnimatedIcon">@drawable/splashscreen_logo</item>
  <item name="postSplashScreenTheme">@style/AppTheme</item>
  <item name="android:windowSplashScreenBehavior">icon_preferred</item>
</style>
```

`AppTheme` is `postSplashScreenTheme` — the theme Android switches `MainActivity` to **the instant the native SplashScreen ends, before React has painted a single pixel**. It extends `Theme.AppCompat.DayNight.NoActionBar` but never sets an explicit `android:windowBackground`. In system dark mode, AppCompat's DayNight resolution falls back to a **dark default window background** for that gap — and since our own JS bootstrap takes real time (Sentry/PostHog/query-persist init run synchronously before first render), that gap is long enough to be clearly visible as a dark flash. Separately, `Theme.App.SplashScreen`'s icon container may render its own opaque/light contrast backdrop behind our fully-transparent placeholder icon regardless of the icon's own transparency — a second, independent source of a "white box." The fix below addresses both at once rather than trying to isolate which one is the true cause, since both are cheap, targeted, low-risk edits.

**Residual risk, stated up front:** some Android launchers (MIUI included) also show their own launch-transition chrome (icon-zoom + dim scrim) *before* an app's own window even attaches, which app theming cannot control. If this fix doesn't fully eliminate the dark+box appearance, that would point to launcher-level chrome rather than our theme — at that point the only remaining lever is shortening actual cold-start time (the performance work already discussed and intentionally deferred). This plan targets everything that *is* within our control.

`android/` is fully gitignored (Expo CNG) and gets regenerated by `npx expo prebuild`, so any manual XML edit is wiped on the next prebuild. The durable fix is a small local Expo config plugin, registered in `app.json`, that patches `styles.xml` programmatically every time prebuild runs.

## Implementation

### 1. New file: `thrivo-mobile/plugins/withAndroidSplashWindowBackground.js`

Plain CommonJS (this repo has no `app.config.ts`/TS-config pipeline — `app.json` is plain JSON — so a `.ts` plugin would need a build step the project doesn't otherwise have; `.js` is the minimal-new-infrastructure choice).

```js
const {
  withAndroidStyles,
  AndroidConfig: {
    Styles: { assignStylesValue, getAppThemeGroup },
  },
} = require("expo/config-plugins");

// Keep in sync with colors.light (src/theme/colors.ts) and the expo-splash-screen
// plugin's backgroundColor in app.json if the brand background ever changes.
const SPLASH_MATCH_COLOR = "#F4F6F9";

/**
 * The RN/Expo template's generated AppTheme never sets an explicit android:windowBackground.
 * AppTheme is postSplashScreenTheme - what Android swaps to the instant the native splash
 * ends, before React paints anything - so in system dark mode it falls back to AppCompat's
 * dark DayNight default for that gap, producing a dark flash before BrandSplash can render.
 * windowSplashScreenIconBackgroundColor is set too, in case the icon container's own
 * contrast backdrop (rather than the AppTheme gap) is the source of the white box - cheap
 * to fix both regardless of which is the true cause.
 *
 * App is intentionally light-mode-only (userInterfaceStyle: "light" in app.json), so this
 * only touches the base values/styles.xml - never a values-night variant.
 */
const withAndroidSplashWindowBackground = (config) => {
  return withAndroidStyles(config, (config) => {
    const xml = config.modResults;

    assignStylesValue(xml, {
      add: true,
      value: SPLASH_MATCH_COLOR,
      name: "android:windowBackground",
      parent: getAppThemeGroup(),
    });

    assignStylesValue(xml, {
      add: true,
      value: SPLASH_MATCH_COLOR,
      name: "windowSplashScreenIconBackgroundColor",
      parent: { name: "Theme.App.SplashScreen" },
    });

    return config;
  });
};

module.exports = withAndroidSplashWindowBackground;
```

API verified directly against `node_modules/@expo/config-plugins/build/android/Styles.d.ts`/`.js`:
- `withAndroidStyles`/`AndroidConfig.Styles.{assignStylesValue, getAppThemeGroup}` are exported from `expo/config-plugins` (re-export of `@expo/config-plugins@54.0.4`, confirmed present as a transitive dep).
- `assignStylesValue(xml, { add, value, name, parent })` mutates `xml` (== `config.modResults`) in place via `setStylesItem`.
- `getAppThemeGroup()` returns `{ name: 'AppTheme' }` without a parent constraint (safe regardless of `edgeToEdgeEnabled` affecting the generated parent chain).
- `Theme.App.SplashScreen` has no exported helper (it's `expo-splash-screen`-specific, not RN-template), so pass `{ name: "Theme.App.SplashScreen" }` directly — `setStylesItem` matches by name and will append to the existing block created by `expo-splash-screen`'s own mod rather than duplicate it.

### 3. Regenerate + rebuild

```bash
cd thrivo-mobile
npx expo prebuild -p android --clean
```

Reapply the manual `android/app/build.gradle` short-path fix (this is a plain Gradle file, not plugin-managed, so it's wiped by every prebuild — same as every prior cycle this session):

```groovy
android {
    ndkVersion rootProject.ext.ndkVersion

    // Local-only workaround: the repo's deep Windows path combined with RN's New
    // Architecture CMake/ninja codegen tree overflows MAX_PATH (260 chars).
    externalNativeBuild {
        cmake {
            buildStagingDirectory "C:/rncxx/thrivo-mobile"
        }
    }
    ...
```

Rebuild release (single-ABI, matching the working recipe established earlier this session):

```bash
rm -rf "C:/rncxx"
cd android
./gradlew.bat app:assembleRelease -x lint -x test --configure-on-demand --build-cache -PreactNativeArchitectures=arm64-v8a
```

Install (MIUI needs Play Protect scanning off and a fast tap on the install prompt — already established this session) and launch:

```bash
adb install -r android/app/build/outputs/apk/release/app-release.apk
adb shell am start -n com.beorchid.thrivo/.MainActivity
```

## Verification

1. **Before installing** — confirm the fix actually landed in the generated XML:
   ```bash
   cat android/app/src/main/res/values/styles.xml
   ```
   Expect `AppTheme` to now include `<item name="android:windowBackground">#F4F6F9</item>`, and `Theme.App.SplashScreen` to include `<item name="windowSplashScreenIconBackgroundColor">#F4F6F9</item>`. Confirm no `values-night/styles.xml` exists (none expected/wanted).

2. **Rule out ART interpreter overhead as a confound** before judging speed or smoothness:
   ```bash
   adb shell cmd package compile -m speed -f com.beorchid.thrivo
   ```

3. **Objective cold-start number** (should be roughly unchanged — this fix changes *what's painted* during the existing gap, not the gap's length):
   ```bash
   adb logcat -c
   adb shell am force-stop com.beorchid.thrivo
   adb shell am start -n com.beorchid.thrivo/.MainActivity
   adb logcat -d | grep Displayed
   ```

4. **Primary verification — the user, physically, on their device**: with system dark mode still on, force-stop the app, swipe it from recents, and reopen it by hand while recording the screen. Confirm: no dark flash, no white/light box distinct from the background, and a seamless flat `#F4F6F9` handoff straight into `BrandSplash`'s gradient. (This session found `adb shell screenrecord` + scripted `am start` unreliable whenever the phone's screen locked between commands — a user-driven manual test is the trustworthy source of truth here, as it was for the very first diagnostic recording.)

5. **Regression check**: relaunch a couple of times with the device back in light mode too, confirming no visual change there (it already looked correct) and that the new `windowSplashScreenIconBackgroundColor` doesn't introduce any new seam against the transparent icon.

If the dark+box appearance persists after this fix, that points to launcher-level (MIUI) launch-transition chrome rather than our app's theme — at that point the only remaining lever is the cold-start performance work already discussed and deferred.
